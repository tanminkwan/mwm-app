# 이메일 발송 기능 기술서 (Email Sending Architecture & Implementation)

본 문서는 사내/외부망 환경에서 안정적이고 시각적으로 깨지지 않는 이메일을 발송하기 위해 고안된 아키텍처와 상세 구현 내용에 대해 설명합니다.

---

## 📌 1. 개요 (Overview)
지식관리(Knowledge) 시스템에 등록된 `HTML` 형태 또는 `Markdown` 형태의 문서와 S3 첨부파일들을 사용자가 지정한 태그(예: 이메일그룹) 또는 직접 입력한 이메일 주소로 전송하는 기능입니다. 메일 서버 환경의 제약(보안 게이트웨이의 CSS 검열, 외부망 이미지 차단 등)을 극복하고, 작성된 본문 포맷 그대로 수신자에게 도달하게 만드는 여러 기술 요소가 결합되어 있습니다.

---

## 🛠️ 2. 사용된 기술 스택 (Technology Stack)

- **`smtplib` & `email.mime` (Python 표준 라이브러리)**: SMTP 프로토콜을 이용해 이메일 원문(MIME 포맷)을 조립하고 메일 서버로 발송합니다.
- **`Markdown` (파이썬 패키지)**: `fenced_code`, `tables`, `toc` 등의 확장을 통해 마크다운 문법을 HTML로 안전하게 렌더링합니다.
- **`Premailer` (파이썬 패키지)**: 인라인 CSS 변환기. `<style>` 블록에 정의된 CSS 규칙들을 파싱하여, 각 HTML DOM 엘리먼트의 `style="..."` 속성 안으로 하드코딩(Inlining)해 줍니다. 
- **`S3 / Boto3`**: 이메일에 물리적으로 포함해야 하는 파일들을 S3 버킷에서 다운로드할 때 사용합니다.
- **`Kroki API (MWM-Kroki)`**: 마크다운 본문에 삽입된 ````mermaid```` (다이어그램) 코드를 외부 렌더링 서버를 통해 실시간으로 `PNG` 이미지 바이너리로 변환해 줍니다.
- **`CID (Content-ID)`**: HTML 내부에 삽입될 이미지를 메일 인라인(Inline) 객체로 포함시키고, `src="cid:..."`로 본문에서 즉시 참조하게 만드는 표준 기술입니다.

---

## ⚙️ 3. 핵심 아키텍처 및 구현 상세

이메일 발송 관련 로직은 결합도를 낮추고 재사용성을 높이기 위해 크게 두 계층으로 분리되어 있습니다.
- **Controller 영역:** `app/views/knowledge.py` (사용자 입력 검증, HTTP 응답 처리)
- **Service/Common 영역:** `app/mail_sender.py` (이메일 파싱, 변환, SMTP 발송 처리)

### 3.1. 메일 수신자 처리 로직 (`get_emails_from_tags`)
단순히 수동으로 입력받은 이메일만 처리하는 것이 아니라, `지식관리 태그(ut_tag)`의 `value1` 필드에 쉼표(,)로 구분되어 미리 저장된 이메일 그룹 목록을 불러와 병합합니디.
- 내부적으로 `list(set(...))`을 사용하여 수동 입력과 태그 그룹 간의 중복된 이메일을 자동으로 1명분으로 압축하여 발송합니다.

### 3.2. S3 첨부파일 바이너리 패치 (`get_attachments_from_s3`)
사용자가 문서에 드래그&드롭으로 올린 파일들의 메타데이터(파일명/S3 Key)를 조회한 후, `S3FileManager`를 통해 S3 상의 실제 바이너리 데이터를 스트리밍하여 메모리로 로딩합니다. MIME 조립 시 `MIMEApplication` 파트로 붙여 메일 첨부파일로 구성하게 됩니다.

### 3.3. Markdown 렌더링 및 다이어그램(Mermaid) 처리 (`convert_md_to_html`)
일반적인 마크다운 파싱을 넘어서, 다이어그램을 지원합니다:
1. **정규식 파싱:** 본문을 탐색하여 ````mermaid```` 블록을 찾습니다.
2. **Kroki 렌더링:** 해당 코드를 zlib으로 압축하고 Base64로 인코딩한 뒤, 사내 KROKI 컨테이너 (`http://mwm-kroki:8000`)에 HTTP 요청을 날려 PNG로 변환된 이미지를 가져옵니다.
3. **MIME 인라인 변환 (CID):** 렌더링 된 이미지를 백령 링크(URL)로 걸지 않고, MIME 메시지 내부의 인라인 청크로 담아 고유 ID(`cid:mermaid_1` 등)를 할당합니다. 외부 이미지 접근이 차단된 폐쇄망 이메일 브라우저에서도 다이어그램이 정상적으로 표시됩니다.

### 3.4. CSS 인라인 변환 메커니즘 (`premailer`)
**문제 상황:** 대부분의 기업형 메일 보안 어플라이언스(IronPort 등)나 MS Exchange 서버는 보안상(XSS 방지) 이유로 이메일 검열 과정에서 HTML의 `<style>...</style>` 블록을 무시하거나 아예 삭제시켜 버립니다. 이로 인해 표(Table)나 글꼴 디자인이 붕괴되는 현상이 발생합니다.
**해결 구현:** 
사전 정의된 테이블 디자인 규칙을 적용한 HTML 변수(`styled_html`)를 SMTP 모듈에 넘기기 전, `premailer.transform(styled_html)`로 포장합니다. 이는 내부적으로 CSS 파서가 작동하여 `table`, `th`, `td` 등의 모든 DOM 구조에 다음과 같이 영구적인 데코레이션을 주입합니다.
> \`<td style="border: 1px solid #999;">TEXT</td>\`


### 3.5. SMTP Envelope-To vs Header (`send_mail`)
메일을 보낼 때 흔히 겪는 수신/참조자 누락 문제를 해결하기 위한 내부 구현입니다.
MIME 프로토콜의 `To:`, `Cc:` 헤더는 오직 메일을 열었을 때 **수신자에게 표시(Display)할 텍스트 껍데기**에 불과합니다. Gmail 등 일부 똑똑한 서버는 이 문자열 헤더를 자기가 파싱하여 참조/수신을 알아내 발송해 주지만, 표준/사내 SMTP 서버는 이를 지원하지 않습니다.
따라서, `app/mail_sender.py`의 구현부에서는 `msg['Cc']` 헤더와는 별개로, **실제 전송 목적지 리스트(Envelope To)인 `all_recipients = receivers + cc` 변수를 만들어 `smtplib.sendmail()`의 두 번째 인자(리스트 파라미터)에 명확히 모두 때려 박아주는** 표준 방식으로 통신을 제어하고 있습니다.

### 3.6. Markdown Editor 이미지 붙여넣기 (Paste Hook) 처리
**문제 상황:** ToastUI Markdown Editor에서 화면을 캡처하여 붙여넣기(`Ctrl+V`)를 하면 에디터 기본 동작에 의해 이미지가 `data:image/png;base64,...` 형태의 어마어마하게 긴 텍스트로 치환되어 문서 가독성을 해치고 입력창을 렉 걸리게 만듭니다.
**해결 구현:**
`add_md2.html` 및 `edit_md2.html`의 에디터 초기화 코드에 `addImageBlobHook` 훅(Hook)을 추가하여 이미지 클립보드 이벤트를 가로챕니다.
1. 이미지가 붙여넣어질 때, 기본 Base64 렌더링 동작을 차단합니다.
2. 해당 이미지 Blob 데이터를 백그라운드 AJAX(`uploadFile` 함수)를 통해 서버의 지정된 첨부파일 업로드 API로 즉시 전송(S3/로컬 저장 등)합니다.
3. 업로드가 완료되면 서버가 반환한 실제 다운로드 URL을 받아 `![이미지](URL)` 형태의 짧고 깔끔한 마크다운 이미지 문법으로 에디터 본문에 자동 반환(`callback`)합니다.
이를 통해 에디터 내용을 깔끔하게 유지하면서도 이미지를 이메일 본문에 정상적으로 포함시킬 수 있는 기반을 마련했습니다.

### 3.7. S3 이미지 인라인 처리 (Inline S3 Fetching)
**문제 상황:** 위 Paste Hook 기술을 통해 에디터에 삽입된 이미지들은 `![이미지](/common/download/파일명)` 형태의 다운로드 API URL로 저장됩니다. 문제는 이 본문 통째로 이메일로 발송할 경우, 이메일을 수신하는 메일 클라이언트(Outlook 등) 및 메일 서버는 사내망 다운로드 URL에 접근할 수 없으며, 설령 도메인이 존재하더라도 세션(로그인)이 없으므로 `HTTP 401/403` 권한 오류가 발생해 이미지가 모두 깨진 엑스박스(X)로 표시됩니다.
**해결 구현:**
이메일 발송 직전, `convert_md_to_html` 모듈에서 정규식 파서를 띄워 본문 내 S3 다운로드 URL 구조를 스캔합니다.
1. `![...](/common/download/...)` 또는 `<img src="/common/download/...">` 패턴이 감지되면 매칭된 파일명을 추출합니다.
2. HTTP 요청 없이 서버 로컬 클래스인 `S3FileManager().get_file(...)`를 직접 호출하여 S3 버킷에서 즉각적으로 이미지의 물리적 바이너리 데이터를 패치(Fetch)합니다.
3. 가져온 이미지 바이너리를 본문의 MIME 청크에 인라인(Inline)으로 추가하고, 고유 `cid:s3img_...` 값을 부여합니다.
4. 원본 텍스트의 URL 부분을 새로 부여한 `cid:...` 로 모두 치환합니다.
이를 통해 수신자는 메일 내부 껍데기에 이미 완전히 캡슐화되어 동봉된 이미지를 열어보게 되므로, 로그인/접근 제어의 영향을 일절 받지 않고 안정적으로 이미지를 렌더링 할 수 있습니다.

### 3.8. MIME 구조 최적화 (MIME Structure Optimization)
**문제 상황:** 인라인 이미지(S3에서 패치한 이미지 및 Mermaid 다이어그램)를 단순히 일반 본문 파일과 함께 메일 최상단 껍데기(`multipart/mixed`)에 부착하여 발송하면, 일부 이메일 뷰어(Outlook, MS Exchange 등)에서 본문에는 이미지를 잘 띄우면서도 해당 이미지를 다시 "일반 첨부파일" 영역에 중복해서 X박스 형태로 노출하는 현상이 발생합니다.
**해결 구현:**
MIME 계층 구조를 규격에 맞게 3단계로 엄격히 분리하여 재구성했습니다.
1. `multipart/related`: 이 캡슐 안에는 오직 **HTML 메인 본문(`text/html`)**과 **해당 본문을 꾸미기 위한 부속 인라인 이미지들(`image/png`, `cid:...`)**만을 모아서 묶어줍니다.
2. `multipart/mixed`: 이메일의 최상위 껍데기로 사용합니다.
3. 조립 방식: 먼저 `related` 패키지 객체를 `mixed` 최상단 껍데기에 붙인 후, 사용자가 순수하게 파일 업로더로 넘긴 **"진짜 일반 첨부파일"**들만 `mixed` 껍데기 바깥쪽 레이어에 별도로 붙입니다.
이러한 계층 구조 최적화를 통해, 이메일 클라이언트가 `related` 파트 안에 묶여있는 이미지 파일들은 "본문 장식용 부속품"으로 정확히 인식하게 만들어 첨부파일 다운로드 리스트에 지저분하게 뜨지 않도록 완벽히 숨김 처리할 수 있습니다.
